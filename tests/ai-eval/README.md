# `.ai` assistant evaluation

Measures how well the in-browser models answer questions with the terminal's
tools, so prompt, tool, and sampling changes are judged on numbers instead of
single runs. Small models vary a lot from run to run; compare variants on the
whole task set with repeats.

```bash
pnpm run eval:ai                                    # all variants, qwen3.5-0.8b, 2 repeats
pnpm run eval:ai -- --model qwen3.5-2b --variants baseline,all --repeat 3
pnpm run eval:ai -- --tasks overview,funnel --variants guided --repeat 1
pnpm run eval:ai -- --variants guided --max-steps 20 --timeout 300  # step limit for every variant
pnpm run eval:ai -- --tasks howto-split,pivot-status,summarize-products --variants default,default-docs --repeat 3
```

The runner builds the library and the browser-test fixture, serves the fixture,
and drives `.ai` in Chromium with WebGPU (new headless mode). The first run
downloads the model into `.ai-eval/profile`; later runs reuse it. Every run is
appended to `.ai-eval/results/<model>-<time>.jsonl`, with the answer, every
query and its result, and a trace of the tool calls; a summary table is printed
at the end. A GPU is needed for usable speed. On macOS the runner keeps the
machine from idle sleep (`caffeinate`) until it exits.

## What is measured

The tasks are questions people ask about their own data, not syntax quizzes.
They run on a small online shop in `data/` (generated by `generate-data.mjs`;
rerun it only to change the data): customers, products, orders, order items,
refunds, and a raw `web_events.csv` with a JSON properties column. The runner
loads every file through the terminal, like files a user drops in, and creates
tables from all but the web events. The data has the problems real exports
have: emails that differ only in case, lowercase country codes, products with a
missing or negative price, and orders whose customer does not exist.

Questions about files and databases on the web use `data/remote` (generated by
`generate-remote.mjs`, which needs the DuckDB CLI for the Parquet and DuckDB
files): weather stations as CSV, their readings as Parquet, weather alerts as
JSON, and a warehouse inventory as a DuckDB database. The runner serves them
at `https://data.example.com/` like a web server that lets browsers read files
(CORS headers and range requests), so these tasks need no network and always
see the same files. A task with `prompts` asks them in one conversation, to
check follow-up questions that do not repeat the URL.

`tasks.mjs` holds 27 tasks in eight groups:

| Group | Tasks |
|---|---|
| Getting oriented | tables and row counts, orders per status |
| Business questions | monthly revenue, top products in Q4, average order value per country, best customers, lapsed customers, discount impact, refund reasons |
| Data quality | duplicate accounts, orphaned orders, missing or negative prices, inconsistent country codes |
| Files | daily visitors, purchases by UTM source (JSON), conversion funnel, all from `web_events.csv` |
| Changes | create a monthly revenue table, export German customers to CSV |
| Files on the web | stations per country (CSV), rows of a Parquet file, alerts per severity (JSON), a follow-up question without the URL |
| A database on the web | attach it, and a question that needs it attached |
| DuckDB features | split a string into a list, pivot orders by status, summary statistics of a table |

Expected answers are not hard-coded: each task has a reference query that runs
in the same DuckDB before the model starts, and tasks that change data are
checked afterwards with a verify query. A task passes on the model's answer or
on the results of queries it actually ran, so a guessed number fails. Where a
question has two sound readings (per account or per person, with or without
orphaned orders), both are accepted. Statements run without confirmation, as in
the terminal; every task starts from freshly created tables and without the
files earlier tasks wrote.

## Variants

Each variant adds one group of changes to the previous one (see
`src/ai/tuning.ts` for the settings):

| Variant | Adds |
|---|---|
| `baseline` | the original behavior |
| `sampling` | temperature 0.6 and presence penalty 1.5 (Qwen's guidance against repetition) |
| `data` | three sample rows per table and the values of short text columns; the columns and first rows of files at URLs in the question |
| `guarded` | asking once to run SQL the answer never ran or that has placeholders; repeated queries skipped; docs attached to function errors; the question's URLs named after a missing-file error; names from the data left out of docs searches |
| `all` | the short step-by-step system prompt with an example |
| `all-no-thinking` | `all` with thinking turned off |
| `guided` | `all` with the guided prompt instead: work from the schema block rather than the catalog, check which table has a column, recover from each kind of error, DuckDB tips (files, JSON, dates, `COPY`), the tool-call budget, and a join example; the tools are described to match |
| `guided-no-thinking` | `guided` with thinking turned off |
| `guided-12-steps`, `guided-16-steps` | `guided` with 12 or 16 model turns per question instead of 8; raise `--timeout` with them |
| `default` | `guided` with 20 model turns: `DEFAULT_TUNING` |
| `default-docs` | `default` with the documentation that matches a how-to question sent along (`docsContext`) |

Variants alternate task by task, so a slowdown on the machine affects all of
them alike.

## Results

`DEFAULT_TUNING` targets the suggested model, Qwen3.5 0.8B, with thinking on,
the guided prompt, and 20 steps. On the 18 tasks with 2 repeats that passed
5 of 36 runs, 108 s per run on average; with thinking off it passed none,
because the model then rarely calls a tool. 0.8B answers single-table
questions (counts per status, missing prices, refund reasons); joins, date
ranges, JSON, and changes need a larger model. Re-run after changing prompts,
tools, tuning, or models, and update `DEFAULT_TUNING` when a variant wins clearly.

On the files and the database on the web (`default`, 3 runs each), 0.8B
passed 10 of 18: the Parquet row count and the follow-up question 3 of 3,
stations per country and the attach-only request 2 of 3, alerts per severity 0
of 3 (it reads the JSON file but filters or groups by the wrong column), and a
question that needs the database attached 0 of 3 (once it created an empty
table with the database's name instead). Since the assistant runs only ATTACH
statements until the question's database is attached, the model attaches it
in almost every run, and the attach-only request passed 3 of 3; the question
that needs the attached database passed 2 of 6, with wrong SQL on the
attached tables in the rest (grouping or joining where the question asks for a
total, or filtering by sample values). A guided-prompt rule against grouping
for totals raised that to 3 of 6 but broke grouping questions, so it was dropped. It passed none of the DuckDB feature
tasks without documentation (0 of 9) and 1 of 9 with it (`default-docs`): the
sections that match a whole question are often off-topic (for splitting a
comma-separated string they show `COPY FROM` a CSV file), and the model
sometimes runs their examples. `docsContext` therefore stays off.
